# ADR-0012 — How an operator proves who they are, and what that buys them

- **Status:** Accepted
- **Date:** 2026-08-28
- **Related:** [ADR-0002](0002-monorepo-and-service-boundaries.md),
  [ADR-0006](0006-event-schema-and-versioning.md),
  [ADR-0007](0007-money-identifiers-and-schema-migrations.md)

## Context

Phase 5 puts mutations on alerts: a transition, an assignment, a note, a disposition. Every one of
them writes an `alert_actions` row whose `actor_id` is `NOT NULL` and whose `actor_role` says what
the actor was at the time — that column exists precisely so an unattributable change to a reviewed
decision is not representable.

Until now nothing has needed an identity. `users` was created in V1 with the comment "carries no
credential of any kind; authentication is not yet decided", and the only row in it is the system
principal. `AlertService.transition` takes the actor as a parameter, which is right for a service
and useless as a boundary: a caller who can name any actor is not authenticated, they are trusted.

Three things have to be settled before an endpoint can exist:

1. **How an operator proves who they are.** The audit trail's value is exactly the confidence in
   that answer.
2. **What the API does with the answer**, given the console is a separate origin and the API is
   stateless behind a container.
3. **What is protected now and what is not**, said out loud rather than left to be discovered.

The frontend rules already fix half of this from the other side: role handling in the console is a
user-experience affordance and **never a security boundary**, and there is a test forbidding session
or authorization state in browser storage.

## Decision

### 1. A username and password are exchanged for a short-lived JWT bearer token

`POST /api/v1/auth/login` takes a username and a password and returns a signed token with an expiry.
Every subsequent request carries it as `Authorization: Bearer <token>`. The token is verified on
each request from its signature alone — no session, no lookup, no shared store.

**Rejected: server-side sessions with a cookie.** They need either sticky sessions or a session
store, which is a second stateful dependency for the one part of the system that has no state of its
own. A cookie across origins also drags in CSRF defences that a bearer header does not need, and the
console is deliberately a separate origin from the API (ADR-0002).

**Rejected: an external identity provider.** Keycloak or a hosted provider is the right answer in a
real deployment and the wrong one here: it is another service to run for a demo whose point is to
show the boundary rather than to outsource it, and `make up` is already six containers.

**Rejected: HTTP Basic on every request.** It sends the credential on every call, gives nothing to
expire, and makes "log out" meaningless.

**Rejected: opaque tokens with a server-side store.** That is a session by another name, with the
same second dependency and the extra lookup on every request.

### 2. Credentials live in their own table, and the system principal has none

V10 adds `user_credentials`: one row per user who can log in, holding a BCrypt hash. It is a
separate table rather than a column on `users` for two reasons.

**A credential is not an attribute of a user.** It has its own lifecycle — rotated, revoked,
absent — and a `users` row without one is a perfectly ordinary state rather than a half-populated
record.

**The system principal must not be able to log in, and this makes that structural.** V1 inserts
`system` so that automated actions have an actor; nothing should ever authenticate as it. With a
nullable column that is a rule somebody has to remember. With a separate table it is the absence of
a row, and the login path cannot find what does not exist.

**BCrypt**, at Spring Security's default strength, through `PasswordEncoder`. Not because it is
fashionable but because the alternative worth having — Argon2 — pulls in an extra dependency for a
demo whose password policy is "generated by `make bootstrap` and never reused".

### 3. Roles are read at login and travel in the token

The token carries the user's roles from `user_roles` as of the moment they logged in. The audit row
records the role the actor held for that action, which is what `ActorRole`'s comment has always
required: a user's roles change, and an audit trail has to say what was true at the time.

**A token therefore outlives a role change by up to its expiry**, which is why the expiry is short
(**30 minutes**, configurable). That is the honest trade for statelessness: a revoked analyst can
finish the half hour they started. Making it shorter costs a login; making it stateless-with-
revocation costs the store this decision exists to avoid.

**Rejected: reading roles from the database on every request.** It re-introduces a lookup per
request, and it makes the audit trail _less_ honest rather than more — an action would be recorded
against the role the user has now rather than the one they were exercising.

### 4. Three roles, and the auditor is enforced on the server

| Role            | May                                                         |
| --------------- | ----------------------------------------------------------- |
| `ANALYST`       | Read everything; work an alert — pick up, note, disposition |
| `ADMINISTRATOR` | Everything an analyst may, plus the administrative close    |
| `AUDITOR`       | Read only. Every mutation is `403`.                         |

`SYSTEM` is not a login role. It exists on `alert_actions` so the pipeline's own actions have an
actor, and there is no credential that can produce it.

The auditor's read-only boundary is **enforced by the API**. The console disabling a button is a
convenience, and the test that matters is the one where an auditor's token is sent to a mutation and
gets a `403`.

### 5. What is protected in Phase 5, and what is deliberately not

**Protected:** every operator endpoint — the alert queue, an alert, its history, and every mutation
on it.

**Not protected, deliberately:** `POST /api/v1/transactions`, the ingestion endpoint. It is a
machine-to-machine surface whose caller is a payment pipeline rather than a person, so an operator's
password buys nothing there; giving it the operator's authentication would be modelling it as
something it is not. It needs its own credential — a service account or a signed request — together
with the rate limits and payload bounds that belong beside it, and that is
later security-hardening work.

**This is a real gap and it is stated rather than glossed:** until Phase 8, anything that can reach
the API can submit a synthetic transaction. It is recorded in
[`KNOWN_ISSUES.md`](../development/KNOWN_ISSUES.md),
and the demo stack binds to localhost.

Also unprotected, and correctly: `/actuator/health/*` (a liveness probe cannot hold a token) and
`POST /api/v1/auth/login` itself.

### 6. The signing secret has no default, and the demo password is generated

`SENTINELFLOW_JWT_SECRET` is required, with no fallback, and startup fails without it — the same
rule `POSTGRES_PASSWORD` already follows and for the same reason: a default secret is a secret
everybody has. It is validated at startup to be long enough for HS256, because a short key makes the
signature weaker in a way nothing else would report.

Demo operators are created by the **application seed**, not by a migration, with their password read
from `SENTINELFLOW_DEMO_OPERATOR_PASSWORD`. A BCrypt hash committed in a migration would be a
credential in the repository and the same one on every machine that ever ran it. `make bootstrap`
generates both values into the git-ignored `.env`, exactly as it already does for PostgreSQL and
Grafana.

## Consequences

- Every alert mutation can name a real actor, and the `alert_actions` row it writes is worth what
  the schema always claimed it was.
- The API stays stateless. Nothing about authentication needs a shared store, so nothing about it
  changes when a second instance is started.
- A token cannot be revoked before it expires. The expiry is the mitigation, and a revocation list
  is Phase 8's to add if the demo ever needs one.
- The console can hold a token in memory and must not put it in browser storage, which is what the
  frontend rules already say and what a test already enforces.
- Ingestion remained open until Phase 8, which is the one place this decision knowingly left
  something undone. [ADR-0017](0017-protecting-the-ingestion-surface.md) closed it on 2026-08-31.

**Amended by [ADR-0017](0017-protecting-the-ingestion-surface.md)** (2026-08-31), which decided the
ingestion credential this ADR deferred. It is a shared key rather than this ADR's mechanism, for the
reason §5 gives: a pipeline is not a person, and giving it an operator's login would model it as one.
Nothing in §§1–4 changes.

**Revisit if:** the demo grows a multi-tenant or per-customer notion of access, which token claims
alone would not carry; a real deployment needs revocation or single sign-on, at which point an
external provider stops being over-engineering and starts being the answer; or Phase 8's ingestion
credential turns out to want the same mechanism, in which case this ADR is amended rather than a
second scheme appearing beside it.
