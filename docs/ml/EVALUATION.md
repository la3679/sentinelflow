# Evaluation

How SentinelFlow's risk model is measured, why it is measured that way, and what the numbers do
and do not support. The measurements themselves come from a run recorded at the bottom;
[`MODEL_CARD.md`](MODEL_CARD.md) is generated by that same run and is regenerated rather than
edited.

**Read the limitations before the numbers.** Everything here is measured on synthetic data whose
labels are a generator's own planted shapes. What is being measured is the pipeline's ability to
recover patterns that were deliberately put there — not its ability to detect fraud.

## The decisions, and where they were made

The evaluation design is [ADR-0010](../adr/0010-model-selection-and-evaluation.md), written before
any of the training code existed so that the rules could not be rationalised once the numbers were
in. This document reports against it rather than restating it.

## What is measured, and what is deliberately not

**PR-AUC (average precision) is the headline.**

**Accuracy is not reported anywhere, and is not present in the metrics object at all.** Under this
class imbalance — roughly 3% positives in the holdout — a model answering "not suspicious" to
everything scores about 97%. That is the model this project exists to argue against, and a number
that exists gets quoted, so it is not computed.

Reported beside PR-AUC: precision, recall, F1, F-beta (β=2), false-positive rate, alert rate and
count, the confusion matrix, the Brier score, and **recall per planted shape**. That last one
matters more than it looks: an aggregate recall of 0.2 could be every shape found one time in five,
or one shape found often and four never found at all. Only the per-shape table distinguishes them,
and they are very different systems.

ROC-AUC is recorded as a secondary metric only. Under heavy imbalance it stays flatteringly high for
a model with poor precision, because the negative class is large enough that many false positives
barely move the false-positive rate.

## The split

Group-disjoint by account **and** time-ordered. Neither property subsumes the other.

**Group-disjoint** because every planted shape is several correlated transactions on one account,
each becoming a labelled row whose features are computed from the others. Splitting an account puts
near-duplicates of a test row into training, and the model is then rewarded for recognising one
specific burst rather than the shape of bursts. That does not merely permit inflated metrics — it
produces them.

**Time-ordered** because group-disjointness alone would happily train on traffic from after the test
period, which production can never do. Training is restricted to before the cutoff and the holdout
to at-or-after it; transactions falling in neither are discarded rather than reused.

**The account sample is stratified on whether an account carries a planted shape after the cutoff.**
This is not a refinement, it is what makes the split work at all — and it was arrived at by two
earlier versions failing on real data:

1. An unstratified quarter of accounts produced a holdout with no planted shapes.
2. Stratifying merely on "carries a shape at all" also failed: all seven held-out positive-carrying
   accounts had their shapes before the cutoff, leaving 40 late positives in the dataset and none in
   the holdout.

Stratifying on the class decides which rows are _evaluated on_, never what the model is _shown_. No
estimator sees a stratum, and no row's features or label change according to which side it landed
on. What it buys is a holdout that can be reported honestly rather than one whose recall is
undefined.

**Leakage is asserted, not assumed.** `test_splitting.py` checks account disjointness across the
final split and across every cross-validation fold, and repeats it across five seeds — a split that
only works for the seed it was written against is a coincidence, not a split.

## The operating point

**Chosen against an alert-volume budget of 1% of scored transactions, not by maximising F1.**

An analyst team is a fixed-capacity queue. "We can review one transaction in a hundred" is a
constraint someone actually has; maximising F1 optimises an arithmetic property of the confusion
matrix that nobody in operations experiences.

The threshold is the corresponding quantile of each candidate's **out-of-fold** scores on the
training rows. Out-of-fold because a model has already seen its own training rows and scores them
optimistically, so a threshold taken from in-fold scores alerts on far more than the budget the
moment it meets rows it has not. **Each candidate gets its own threshold**: two models can rank
identically and still place their scores at completely different absolute values, so one shared
threshold would compare two different alert volumes.

**The holdout never chooses anything.** It is scored once, at the threshold already fixed on the
training folds.

**The alert budget is an assumption, not a measurement.** It stands for a review capacity nobody has
measured here, and every precision, recall and false-positive figure moves if it moves.

## The selection rule, fixed in advance

1. The holdout must contain at least **20 positives**. Below that, nothing is promoted — see
   "Refusals" below.
2. A model ships only if it beats the rules baseline's PR-AUC by at least **0.05** absolute. If none
   does, **the rules baseline ships alone** and the models are recorded as evaluated and not
   promoted. Having built a model is not a reason to serve one.
3. Between qualifying models the best holdout PR-AUC leads — unless the gap to the simpler model is
   inside the cross-validation fold spread, in which case it is not distinguishable from fold noise
   and the simpler model wins, for its inference cost and per-feature explainability.

`IsolationForest` is compared and is **not eligible to ship**. Its anomaly score is unbounded and
dataset-relative, so giving it a stable meaning on the contract's 0-to-100 scale would require
calibrating it against the labels it was included for being able to ignore. It is reported because
"how much of this structure is visible without labels at all" is worth knowing.

## Refusals

The pipeline stops rather than producing a number it cannot support. Each of these was added because
it fired on real data:

| Refusal                                   | Why                                                                            |
| ----------------------------------------- | ------------------------------------------------------------------------------ |
| Holdout has no positives                  | Recall over zero positives is undefined; 0.0 and 1.0 are both inventions       |
| Holdout has fewer than 20 positives       | Every metric swings by large amounts on one example — see below                |
| Training set has no positives             | Nothing for a supervised model to learn                                        |
| Dataset has no positives at all           | Trains a model that answers "no" to everything and scores well on accuracy     |
| A line is not a valid `ScoreRequest`      | Named by line number, because "a field is missing somewhere" is not actionable |
| Manifest has no `negativeLabel`           | Which class is positive would be a guess in Python about a decision in Java    |
| Artifact checksum does not match          | The file on disk is not the one the metrics beside it describe                 |
| Artifact's feature version is not current | Columns would still line up by position and scores would still look reasonable |

**The 20-positive floor was found by running the pipeline, not by reasoning about it.** On the DEMO
profile the holdout contains three positives, and the selected model's PR-AUC moved from 0.06 to
0.39 on the difference between finding one of them and none. Nothing about those numbers was
fabricated, and reporting them would still have been dishonest: they would have been presented as
evidence while being incapable of supporting a conclusion. Twenty is a floor below which the
pipeline refuses to publish, not a claim that twenty is enough — the model card states the count
either way so a reader can judge for themselves.

## The measured run

Run on **2026-08-26**, seed `20260826`, profile `LOCAL`, feature version `1.0.0`, generator version
`1.1.0`.

```text
make seed                 # SENTINELFLOW_SEED_PROFILE=LOCAL
make export-dataset
cd apps/scoring && uv run python -m sentinelflow_scoring.training
```

- Dataset: **20,707** labelled examples, **707** planted, 19 features.
- Split: **7,876** training rows, **2,499** holdout rows, cutoff `2026-08-19T22:54:15`.
- Holdout class balance: **75** positives, **2,424** negatives (3.0%).

| Model                     | Holdout PR-AUC | CV fold mean | CV spread | Eligible         |
| ------------------------- | -------------- | ------------ | --------- | ---------------- |
| `rules-baseline`          | 0.2611         | —            | —         | floor            |
| **`logistic-regression`** | **0.8327**     | 0.8867       | 0.0723    | **selected**     |
| `hist-gradient-boosting`  | 0.8081         | 0.8841       | 0.0814    | yes              |
| `isolation-forest`        | 0.7154         | 0.7840       | 0.1035    | no (ADR-0010 §4) |

Logistic regression was selected: it has the best holdout PR-AUC among qualifying models and is also
the simplest, so the tie-break never had to be applied.

At the operating point (`99.99986221` on the 0-to-100 scale), the selected model gives precision
1.000, recall 0.200, a false-positive rate of 0.000 and an alert rate of 0.60% against the 1%
budget. The rules baseline at its own budgeted point gives precision 0.722 and recall 0.173.

Full numbers, including the per-shape recall table and every candidate's metrics, are in
`apps/scoring/models/logistic-regression/1.0.0/metrics.json`. The plots are beside it.

## Limitations

**These are the most important part of this document.**

- **This is synthetic data and the labels are a generator's planted shapes.** The measurement is of
  pattern recovery, not fraud detection. It is not comparable to any published benchmark and does
  not reproduce any organisation's reported figures.
- **The alert budget is an assumption.** Every precision, recall and false-positive number is _at
  that budget_.
- **The score distribution is heavily saturated and the operating point sits in that region.** Most
  transactions score near zero and a small group scores within a fraction of 100. Measured on this
  run, thresholds of 99.99, 99.0 and 95.0 give recalls of 0.32, 0.48 and 0.53 over the same holdout,
  with precision at 1.000 throughout — so the trade is recall against alert volume rather than
  against false positives, but the sensitivity is real. A deployment should choose its threshold
  from the volume it can absorb, not by copying the number above.
- **Calibration is good where there is data and noisy where there is not.** The reliability curve
  sits on the diagonal in the bottom and top bins, which hold nearly all the mass, and swings
  between 0 and 1 in the sparse middle bins. The plot sizes each marker by its bin count so this is
  visible rather than something a reader has to know.
- **`balanceDrainRatio` is measured against a balance that never changes.** Nothing in SentinelFlow
  mutates an account balance, so each transaction's drain ratio is against the account's opening
  balance rather than a running one. An `ACCOUNT_DRAIN` therefore reads as several independent
  partial drains rather than one cumulative emptying; the velocity and one-hour-sum features carry
  that shape instead.
- **Rapid fan-in is not expressible in the data at all.** `transactions` records an account and a
  merchant with no counterparty account, so that pattern is absent rather than undetected. See
  [`DATA_PROVENANCE.md`](../data/DATA_PROVENANCE.md).
- **The holdout is small in accounts.** A group-disjoint split spends the dataset in accounts rather
  than rows, so the interval around every figure is wider than 2,499 rows suggests.
- **F-beta at β=2 encodes a cost assumption** about a missed case versus a wasted review that no
  measurement here supports.
- **The baseline is now the ruleset that ships, and the earlier figure was too generous.** Until
  2026-08-27 this comparison used a Python stand-in in `apps/scoring`, which scored the same holdout
  at PR-AUC **0.1535** where `apps/api`'s ruleset — the one that runs in-process when scoring is
  unreachable — scores **0.2611**. Every previously published margin over "the rules" was therefore
  measured against something weaker than the rules, by roughly 0.11 PR-AUC. The stand-in has been
  deleted rather than replaced: `apps/api` evaluates every example with `RuleEngine` as the labelled
  dataset is exported, and the trainer reads the column. Two rule implementations would have
  drifted, and the drift would have shown as a model beating a baseline nobody runs.
- **The rule score is a comparison column and never a feature.** It is not part of `ScoreRequest`, so
  the extractor cannot see it. A model trained on it would be partly modelling the rules, and beating
  them would then mean very little.

## Reproducing this

Training is an explicit offline command and never an API side effect (§12.6). The manifest beside
the model records the dataset fingerprint, the seed, the feature version, the split strategy, the
hyperparameters, the environment lock hash and the artifact checksum.

**The checksum proves the loaded artifact is the evaluated artifact. It does not claim
byte-reproducible retraining** — joblib output depends on library build details that vary across
platforms, and claiming otherwise would be a guarantee this project cannot honour. What is
reproducible is the metrics, from a fixed seed over a fingerprinted dataset.
